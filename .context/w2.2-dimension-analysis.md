# W2.2 Part B — the `EMBEDDING_DIMENSIONS` pin

**Recommendation: do not migrate. Keep the fixed `VECTOR(1536)` column, delete
`EMBEDDING_DIMENSIONS` as a knob, and move the failure from insert time to
startup.**

**Deciding factor:** pgvector cannot build an HNSW or IVFFlat index on an
unsized `vector` column in any released version, and the only in-place path to
one produces a database that `pg_dump`/`pg_restore` cannot reproduce. Every
remaining option is a fixed dimension wearing a different hat, and none of them
unblocks an operator that `EMBEDDING_API_BASE` (Part A) does not already
unblock.

No migration is included in this work unit. `sql/migrations/0009_*.sql` is not
written.

---

## 1. What was measured, and how

Everything in this section was run against the **exact image the deploy bundle
pins** — `pgvector/pgvector:pg17@sha256:d2ef61f4…3bad0`, which resolves to
**pgvector 0.8.5 on PostgreSQL 17.10**. A second, independent check against the
floating `pgvector/pgvector:pg17` tag (currently **0.8.6**) produced identical
results, and the relevant guard is unchanged in pgvector source from v0.1.0
(IVFFlat) and v0.5.0 (HNSW) through today. These are not version-sensitive
findings.

| # | Statement | Result |
|---|---|---|
| 1 | `CREATE TABLE t (embedding vector NOT NULL)` | **works**; rows of 3 and 5 dims coexist in one column |
| 2 | `CREATE INDEX … USING hnsw (embedding vector_cosine_ops)` on that column | **`ERROR: column does not have dimensions`** |
| 3 | same with `ivfflat` | **same error** |
| 4 | `CREATE INDEX … USING hnsw ((embedding::vector(3)) …)` over mixed-dim rows | `ERROR: expected 3 dimensions, not 5` |
| 5 | the same expression index made **partial**, `WHERE vector_dims(embedding) = 3` | **works**, and the planner uses it (`Index Scan using t_unsized_expr3`) |
| 6 | `ALTER … TYPE vector` from `vector(3)`, HNSW index present | succeeds, **no table rewrite**, and the HNSW index **survives and stays valid** |
| 7 | inserting a 5-dim row into that column afterwards | `ERROR: different vector dimensions 5 and 3` — the surviving index still pins the width |
| 8 | `REINDEX` on that surviving index | **`ERROR: column does not have dimensions`** |
| 9 | `ALTER … TYPE vector(768)` with 3-dim rows present | `ERROR: expected 768 dimensions, not 3` |
| 10 | attaching a `vector(1536)` partition to a `vector` partitioned table | `ERROR: child table … has different type for column "embedding"` |
| 11 | HNSW ceiling | 2,000 for `vector`, 4,000 for `halfvec`, 64,000 for `bit`; `vector` column max 16,000 |
| 12 | a `DO` block in a migration branching on `current_setting('diffuse.…', true)` | mechanism works; the migration file's bytes, and therefore its checksum, stay identical across installs |

Row 8 is the finding that decides this. Rows 6–8 together describe a state that
`CREATE INDEX` cannot produce, `REINDEX` cannot rebuild, and `pg_dump` emits as
SQL that fails on restore:

```sql
-- what pg_dump --schema-only writes after the "widen it in place" migration
CREATE TABLE public.code_chunks (…, embedding public.vector, …);
CREATE INDEX code_chunks_embedding_hnsw_idx
    ON public.code_chunks USING hnsw (embedding public.vector_cosine_ops);
-- ERROR:  column does not have dimensions
```

A Diffuse install that has applied that migration has a working database that
cannot be restored from its own backup. That is a worse outcome than the bug
being fixed.

## 2. Why this is not simply a schema bug

`index_snapshots.embedding_dimensions` already exists, and
`indexer/store.py` and `retriever/retrieve.py` already select an active snapshot
by `(embedding_model, embedding_dimensions)`. The *logical* layer is genuinely
per-snapshot: a snapshot built at the wrong width is invisible to retrieval
rather than mixed into it.

The storage layer cannot follow, because `VECTOR(n)` is a fixed-dimension type
and `code_chunks` has one `embedding` column shared by every snapshot of every
repository. The `CHECK (embedding_dimensions = 1536)` on `index_snapshots` is
not the pin; it is documentation of the pin. Removing it changes nothing:
`code_chunks.embedding VECTOR(1536)` still rejects the row.

Blast radius is small and worth stating, because it makes some options cheaper
than they look. Exactly **one** query in the tree performs a vector distance
comparison — `indexer/store.py:770-773`:

```sql
1 - (embedding <=> %s::vector) AS similarity
…
ORDER BY embedding <=> %s::vector
```

and exactly **one** statement writes vectors, `upsert_chunks`, with a
`%s::vector` cast in its template. Any option below that changes the query
expression touches two call sites, not twenty.

## 3. Options

### Option 1 — fixed dimension chosen once, at install time, by the migration

The migration sets the typmod from a value the operator supplies before the
first migration runs, and startup validation fails loudly on mismatch
thereafter.

The checksum contract is not an obstacle, which surprised me. Migration files
are byte-identical across installs and their SHA-256 is verified against the
recorded value, so the SQL cannot be templated per install — but a `DO` block
reading a session GUC keeps the bytes identical while producing a different
type (row 12). `migrate_database` already runs everything inside one
transaction under `pg_advisory_xact_lock`, so a `SET LOCAL
diffuse.embedding_dimensions` before `cursor.execute(migration.sql)` would work
with a few lines of change.

What kills it is not the mechanism, it is what the mechanism buys:

- **It is not a knob, it is a one-way door.** Row 9: changing the typmod with
  rows present is a hard error, and even on an empty table it is a full rewrite
  under `AccessExclusiveLock`. Changing an install's dimension means truncating
  `code_chunks` and re-indexing every repository from scratch. Calling that
  "configurable" repeats the exact honesty problem this unit exists to fix,
  one level up.
- **It makes two installs at the same schema version structurally different,
  invisibly.** `_verify_baseline_contract` compares table and column *names*
  only — it would not notice that one install is `vector(1536)` and another is
  `vector(1024)`. The migrator's own drift detection would be blind to the one
  thing that had become install-specific. Every future migration touching
  `code_chunks`, every bug report, and every support conversation would have to
  start by asking which width this install chose.
- **It solves a problem nobody currently has.** Part A's `EMBEDDING_API_BASE` is
  what unblocks the Anthropic-only and self-hosted operators. What remains is
  the narrower case of an operator whose only available embedding model is not
  1,536 wide. That is real but hypothetical here, and it is cheaply worked
  around: most self-hosted servers can truncate (Matryoshka models), and
  `text-embedding-3-large` accepts a `dimensions` parameter.

The *second half* of this option — startup validation instead of insert-time
failure — is unambiguously good and is independent of the first half. See
"What this PR does instead".

### Option 2 — unsized `VECTOR` column

**Non-starter as stated, and non-starter in its salvageable form too.**

Rows 2 and 3: no HNSW, no IVFFlat, hard error, unchanged since the feature
existed. pgvector's own README says so:

> You can use `vector` as the type (instead of `vector(n)`). However, you can
> only create indexes on rows with the same number of dimensions (using
> expression and partial indexing)

Losing the ANN index is not a performance regression to be measured; it is a
sequential scan plus a full sort over every chunk of every snapshot on every
retrieval, which is the whole product.

The salvageable form is row 5: one **partial expression** index per dimension,
`USING hnsw ((embedding::vector(N)) vector_cosine_ops) WHERE vector_dims(embedding) = N`.
This genuinely works and the planner genuinely uses it. It still fails, for four
reasons:

1. **Migration path.** Row 6/8: the in-place widen leaves an index that cannot
   be rebuilt and a database that cannot be restored from its own dump. Doing it
   safely means `DROP INDEX` → `ALTER` → `CREATE INDEX` (partial, per
   dimension), all non-`CONCURRENTLY` because migrations run in a transaction,
   which is an `AccessExclusiveLock`-scale HNSW rebuild over the entire
   `code_chunks` table with the fleet stopped.
2. **New dimensions need new DDL, at runtime.** A migration can only create
   indexes for dimensions known when it was written. Supporting an arbitrary
   width means the worker issues `CREATE INDEX` the first time it sees one —
   DDL from the job path, a multi-minute non-concurrent build holding a lock
   that blocks every other indexing job, or a `CONCURRENTLY` build outside a
   transaction with its own failure and retry semantics. Neither belongs in a
   worker.
3. **The failure mode gets quieter, not louder.** Today a wrong-width vector is
   rejected at insert with a specific message. On an unsized column it is
   *stored* and then excluded from every partial index — so it is silently
   invisible to retrieval. Reviews would run against a repository that looks
   indexed and returns no context. That is strictly harder to diagnose than the
   bug we started with.
4. **Every query needs both halves.** The cast and the `WHERE vector_dims(…) = N`
   predicate must both appear or the index is not used. Two call sites, so it is
   cheap — but it is now impossible to write a correct ad-hoc query against
   `code_chunks` by hand without knowing the convention.

### Option 3 — per-dimension partitions, or per-dimension columns

**Partitioning is impossible**, not merely awkward. Row 10: PostgreSQL requires
every partition to have the identical column type as the parent, so a
`vector(1536)` partition and a `vector(1024)` partition cannot belong to one
partitioned table. The only version of "partitioning" that works here is
unrelated physical tables with templated names, which means templated FKs,
templated indexes, templated queries, and unbounded table proliferation — for a
feature with no current user.

**Separate columns** (`embedding_1536`, `embedding_1024`, …) is coherent and
strictly worse than Option 1: each needs its own HNSW index, every row carries
NULLs for the widths it is not, and adding a width is still a migration *plus* a
code change. It buys the ability to hold two widths at once, which nothing in
Diffuse needs — snapshot selection already treats a mismatched width as
incompatible rather than as something to hold alongside.

### Option 4 — remove the knob; 1,536 is a requirement

Delete `EMBEDDING_DIMENSIONS` as configuration, keep `VECTOR(1536)`, and say so
plainly in the environment reference and the README.

This is the honest description of what already ships. `deploy/env.example`
already says "changing either of these is not supported in this release" — the
variable is a promise the schema does not keep. The cost of the option is
exactly the capability that is currently advertised and non-functional, which
is not a cost.

## 4. Recommendation

**Option 4, with the startup-validation half of Option 1.** Concretely:

1. **No migration in this unit.** `sql/schema.sql` keeps `VECTOR(1536)` and
   `index_snapshots.embedding_dimensions` keeps its `CHECK`. The
   `embedding_dimensions` column stays — it is not dead, it is what makes
   snapshot compatibility checks work if the width ever does change, and it is
   the only thing that would let an install detect a stale snapshot after a
   future re-index.
2. **Fail at startup, not at insert.** `EMBEDDING_DIMENSIONS` set to anything
   other than 1536 stops the worker by name, alongside the other hot-path
   configuration probes, instead of dead-lettering the first index job with a
   pgvector type error. This is the concrete improvement available today and it
   carries no schema risk. Anyone it newly stops was already completely broken.
3. **Say 1,536 out loud** in `.env.example`, `deploy/env.example`, and
   `docs/capabilities.md`, including *why* — so the next person to read
   `EMBEDDING_DIMENSIONS` does not have to rediscover this.
4. **Leave the door open, deliberately.** If a real operator turns up who cannot
   produce 1,536 dimensions, Option 1 is the path: a `0009` migration with a
   `DO` block on a session GUC, `migrate_database` setting it, and a hard
   requirement that `code_chunks` is empty. That is a small change *when there
   is a requirement to size it against*. Building it now means guessing at the
   width, the upgrade story, and the support model simultaneously.

Explicitly **not** recommended for any future release: widening `code_chunks.embedding`
to an unsized `vector` in place. Rows 6–8 make that a one-way trip to a database
that cannot be restored from its own backup.

## 5. Two things to fix regardless

- **`docker-compose.yml` uses a floating `pgvector/pgvector:pg17` tag** while
  `deploy/compose.yaml` pins a digest. The floating tag moved from 0.8.5 to
  0.8.6 during this investigation. 0.8.2 fixed a parallel-HNSW buffer overflow
  (CVE-2026-3172) and 0.8.3 fixed possible HNSW index corruption under vacuum,
  so the digest pinned in `deploy/env.example` should be re-verified against
  >= 0.8.3 and refreshed on a schedule. Out of scope for W2.2; worth a ticket.
- **`README.md:167-171` and `docs/capabilities.md`** both describe the pin
  correctly but present it as a thing a future release "must add a numbered
  migration for". That is true and should stay, but it currently reads as
  though the migration is the only obstacle. It is not: the migration is easy
  and the *dimension change on a populated install* is the hard part, because
  it is a truncate-and-re-index.
